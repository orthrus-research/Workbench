# Trust and authority

Workbench keeps observation, construction, teaching, validation, policy, and
presentation separate. Every consequential result should say which authority
supports it, what scope was examined, and where the claim stops.

## Authority map

| Concern | Authority | Workbench responsibility |
| --- | --- | --- |
| What exists or behaved in an assembled system | Atlas | Preserve identity, evidence scope, uncertainty, and limitations |
| What implementation may be constructed | Blueprints | Use a stable standard or a clearly labeled experimental pattern |
| How a system should be understood | Manuals | Teach from evidence without authorizing code |
| What happened in a controlled run | Crucible | Preserve the fixture, action, capture, and completion boundary |
| How source and runtime identities are handed between tools | Relay | Preserve the binding without elevating an unmatched observation |
| Whether a declared rule is violated | The named platform, pack, Blueprint, or Sentinel policy | Expose the exact rule and consequence |
| Whether a candidate worked | Compiler, focused checks, smoke runs, and required regressions | Report failures as failures |
| How a capability is presented | Workbench core and clients | Preserve all upstream identities and limits |

Workbench orchestrates these authorities. It does not create a second store of
mechanical facts or a second approval path.

## Evidence states

An empty result is not an evidence state. Public surfaces preserve at least:

- **known** — supported for the declared identity and scope;
- **known absent** — sufficient authority and coverage support the negative;
- **unavailable** — the required authority or capture does not exist;
- **unresolved** — relevant evidence exists but does not close the question;
- **bounded** — complete only inside declared limits;
- **truncated** — valid results exist beyond what was retained;
- **inapplicable** — the capability does not apply to this target; and
- **conflicted** — applicable authorities disagree or cannot be composed.

Clients must not flatten these states into success, failure, or a blank view.

## Convention lifecycle

```text
observed pattern
  -> evidence-backed explanation
  -> labeled experiment
  -> compile, run, and debug
  -> admitted standard or declared policy
```

Atlas may describe a pattern. Manuals may explain it. Neither act makes the
pattern normative. Blueprints may use the strongest known pattern in a labeled
experiment, but only an admitted standard authorizes stable construction.
Policy enforcement likewise requires a declared rule; rarity and automated
opinion are not policy.

## Non-negotiable boundaries

Workbench must not:

- remove platform, pack, snapshot, side, target, or source qualification;
- convert static occurrence or presentation into runtime causation;
- hide traversal limits, unresolved leaves, conflicts, or missing evidence;
- merge historical Forge and current Cleanroom observations;
- present an inferred pattern as a stable standard;
- silently migrate a target to a different standard or platform profile;
- treat registered structure as formed-world state;
- claim global optimality from a bounded route or single fixture;
- conceal a crash, corrupt output, build failure, or failed required check;
  or
- treat one experimental success as support for every profile and case.

Detailed composition rules belong with the owning feature architecture, not
in this product-level document.

## Controlled runtime evidence

A Crucible result is authoritative only for its retained fixture, environment,
action, capture, and observation scope. Streaming or partial output remains
provisional until required artifacts, identity bindings, coverage checks, and
completion conditions succeed.

Derived graphs, indexes, semantic fingerprints, and views are rebuildable
projections. They cannot replace exact evidence required by an owning
contract. Crucible may provide deterministic storage and materialization
without becoming Atlas interpretation, Blueprint admission, or pack policy.

Relay preserves exact identity during navigation. It does not make an
uncontrolled world, manually edited runtime, or name-matched UI object
equivalent to a reproducible capture. Required construction and validation use
disposable or explicitly authorized environments.

## Agent-independent operation

Workbench's authoritative path is deterministic and usable without an AI
agent, prompt file, private planning ledger, or coordination harness. Public
behavior is expressed through versioned code, schemas, profiles, contracts,
commands, and tests.

Optional automation may help a developer find a capability, phrase a query,
summarize a result, draft reviewed parameters, run tests, or explain a
failure. It may not create evidence, invent policy, admit a standard, approve
a mutation, report a failed gate as passed, or replace deterministic output.

Local workflow metadata is not product input and is excluded from source and
release packages.

## Consent and mutation

Querying and diagnosis are read-only. A mutation path preserves:

- the exact target and authorized scope;
- the selected construction identity and maturity;
- a complete reviewable preview;
- explicit developer consent;
- protection against target drift;
- atomicity or a stated recovery path;
- post-change verification; and
- a useful record of intended and observed changes.

An IDE action is a presentation convenience, not implicit consent. Equivalent
input through the CLI or either IDE client must reach the same core lifecycle.

## Local custody and privacy

Source, dependencies, build output, logs, crash reports, runtime captures,
worlds, credentials, and retained evidence can be private or large. The
default rules are:

- authoritative local operation requires neither telemetry nor a hosted
  service;
- data remains local unless the developer authorizes a named destination and
  purpose;
- credentials never become evidence, parameters, telemetry, or documentation;
- remote processing or upload is visible before it occurs;
- telemetry, if offered, is opt-in, minimal, and non-authoritative;
- generated targets, worlds, caches, sessions, captures, and proof payloads
  remain in ignored or external storage; and
- an IDE permission, account session, or open project does not imply upload
  consent.

## Reproducibility

A strong result identifies the selected platform and pack profiles, target and
snapshot, request and authority, evidence and validation scope, produced or
observed artifacts, limitation state, and the boundary beyond which no claim
is made.

Proof is not a badge. It is an inspectable explanation of why a bounded result
may be trusted without copying private or bulky evidence into source control.
