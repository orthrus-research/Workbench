# Workbench glossary

## Product and authority

**Workbench** — the local CleanroomMC development suite that orchestrates
knowledge, construction, teaching, controlled validation, and developer
surfaces. It is not a second truth or approval authority.

**Workbench core** — the independently runnable local implementation used by
the CLI, VS Code extension, and IntelliJ plugin.

**client** — a presentation layer that invokes core contracts. A client may
collect input and show review state, but cannot weaken authority or consent.

**Project Intelligence** — identifies the workspace, repositories, build,
profiles, layout, dependencies, and ownership applicable to a project.

**Atlas** — authority for accepted observed and derived knowledge, including
evidence scope, relationships, uncertainty, and limitations.

**Blueprints** — authority for construction from admitted standards or
clearly labeled experimental patterns.

**Manuals** — deterministic, evidence-backed teaching. Manuals never
authorizes code.

**Crucible** — controlled experimentation and retention of reproducible
runtime evidence in disposable or explicitly authorized environments.

**Relay** — identity-preserving navigation between source, runtime evidence,
and developer surfaces.

**Sentinel** — diagnostics backed by an exact declared invariant, policy,
standard, or compatibility authority.

**Studio** — a task-oriented composition of existing capabilities. A Studio
does not become a new knowledge, construction, validation, or teaching
authority.

**authority boundary** — the limit on what a source, module, record, or result
is allowed to establish.

## Platform and profile

**CleanroomMC** — the canonical platform for supported Workbench Minecraft
1.12.2 construction.

**platform profile** — an exact binding of Minecraft, Cleanroom, Java,
bytecode, mappings, build provider, transformation environment, artifacts,
sides, launch assumptions, and compatibility limits.

**pack profile** — an explicit binding of a pack's identity, layout, evidence,
standards, diagnostics, fixtures, and compatibility policy.

**Supersymmetry profile** — Workbench's first pack profile. It is selected
explicitly and is never a universal default inside generic modules.

**legacy Forge profile** — an exact historical or migration environment. Its
evidence remains valid for that profile but cannot substitute for Cleanroom
release evidence.

**host Java** — the JVM running Workbench or its host environment.

**build Java** — the JVM executing the project build.

**source language level** — Java features permitted in authored source.

**target bytecode** — the classfile level emitted by the build or transform.

**runtime Java** — the JVM running the Cleanroom client or server.

## Standards and evidence

**observed pattern** — a recurring source or runtime form supported by
evidence. It is descriptive until separately admitted as a standard or
policy.

**implementation standard** — a named, reviewed Blueprint authority defining
how a feature family is constructed and validated.

**policy** — a declared rule that authorizes a diagnostic or constraint.
Frequency, rarity, and automated judgment are not policies.

**convention** — a platform or project practice whose status is explicit:
observed, explained, admitted, enforced, optional, disputed, or unresolved.

**known** — supported by accepted evidence for the declared identity and
scope.

**known absent** — a negative supported by sufficient authority and coverage.

**unavailable** — required authority or evidence does not exist for the
request.

**unresolved** — relevant evidence exists but does not close the request.

**bounded** — complete only inside declared limits.

**truncated** — valid results exist beyond what was retained.

**conflicted** — applicable authorities disagree or cannot be composed.

**profile gap** — a capability or observation exists for one exact profile
but is unavailable for another.

**causal closure** — an evidence-valid path from an exact source or operation
through lifecycle transitions to an exact runtime result.

## Runtime and graph custody

**controlled fixture** — a disposable, exact environment used to produce
bounded validation or runtime evidence without risking a developer's live
world.

**snapshot** — an immutable binding of exact source, platform, pack, tool,
artifact, side, and policy identities.

**materialization** — a filesystem or runtime target created from a snapshot.

**observation** — a retained account of what happened after a materialization
was exercised.

**registered structure** — the declared runtime definition of an allowed
machine structure. It does not prove that a placement formed in a world.

**formed-world state** — evidence for one exact placed machine, including its
formation and relevant runtime conditions.

**transport normalization** — Crucible's lossless conversion of admitted
producer output into a canonical capture record. It does not interpret
behavior.

**semantic normalization** — an owning authority's deterministic mapping from
evidence into its vocabulary. Atlas owns semantic normalization of game
knowledge.

**evidence-set revision** — an immutable content-addressed manifest over one
accepted evidence set and its lineage.

**graph revision** — an immutable content-addressed graph with exact owner,
schema, inputs, recipe, scope, evidence state, limitations, and lineage.

**current reference** — a mutable convenience pointer to an immutable
revision. The pointer is neither evidence nor part of that revision's
identity.

## Developer experience

**semantic equivalence** — equivalent authoritative input yields equivalent
meaning through the CLI and both IDE clients.

**consent boundary** — the explicit point where a developer authorizes a
material change to an exact target.

**reproduction record** — a compact binding of target, selected construction,
change, environment, checks, and observed result.
