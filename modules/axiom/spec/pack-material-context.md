# Pack material context

The saved-workspace command has two explicit native contexts. Neither yet
qualifies the required-stack initialization MVP; full Supersymmetry pack parity
is not its acceptance target. The [MVP contract](initialization-mvp.md) defines
the supported stack, declared scope and delivery order.

| Context | Execution boundary |
| --- | --- |
| `supersymmetry:material-authoring-gt-base` | Existing bounded GT material programs and their regression evidence; no addon material lifecycle. |
| `supersymmetry:material-authoring-pack` | Original raw SERVER construction, preInit and recipe initialization through AVAILABLE, with real native owners and complete stored GT/crafting/furnace evidence; installed recipe workflow acceptance remains open. |

The profile catalog owns selection and pending-composition metadata. Both contexts
share an authoring vocabulary, but have distinct admission identities. The runtime
builder accepts `--context`; the installed command verifies the selected runtime
against the installed profile. A candidate cannot replace these authorities.
Adding a catalog entry does not provision a runtime or claim it is complete.

The pack profile selects `initializationStage: recipes`. The command executes
original raw SERVER construction, preInit, recipe registry events, initialization,
postInit and load-complete on the same native state. It observes the effective GT,
crafting and furnace registries after those producers/removers return. Prepared
pack runtimes must be rebuilt when profile, engine or packaged source bindings
change. Core owns acquisition, assembly and reuse of the selected original inputs.

A complete supported scope may retain original pack errors. Its initialization
status is `native-failed`; it is neither a clean pass nor proof of invalid saved
source. Saved-source errors retain their locations, and missing required inputs,
unexplained failures or incomplete observations keep the scope incomplete. Stored
callbacks are observed without executing deferred crafting or world behavior.
Installed Core acceptance covers the ordinary saved baseline, native runtime and
compiler failures with retained source, and refusal of a missing required JAR.
The full saved recipe edit matrix and recipe IDE consumption remain open. The
complete CLI response exceeds Node's single-string capacity. Exact previously
acquired inputs support installed assembly; fresh remote acquisition of the
expanded context remains unqualified after a pinned addon URL returned HTTP 403.
The detailed composition evidence below retains its historical scope.

## Required-stack boundary

GroovyScript, CleanroomMC/Forge infrastructure (including MixinBooter and
IVToolkit), GTCEu, GCYM, Susy-Core, SussyPatches and Supercritical are required
targets. Their relevant native compilation, loading, transformations, callbacks
and registry effects must compose faithfully. Axiom does not replace the loader
or substitute handwritten material/recipe behavior.

An ordinary saved checkout is the input; the explicitly declared supported
initialization scope is the acceptance unit. Preserve source/configuration and
native integration conditions. Other libraries or mods are dependencies only
where the checked operations require their behavior. Existing GTFO/Baubles/API
inputs remain evidence and are not removed by this scope clarification; neither
their inclusion nor a broad artifact inventory makes every mod's lifecycle an
MVP gate. LadyLib/Gaspunk remains tertiary unless a supported operation needs it.
Do not fabricate presence or registration effects to avoid a real dependency.

This is a target boundary, not a change to current runtime admission, result
codes or qualification. Unrelated deferred work may eventually coexist with a
successful scoped result; any gap affecting that scope must remain incomplete.

## Native dependencies

Local API input assembly verifies artifacts against the immutable selected pack's
metadata. It retains original class bytes from GTCEu, GroovyScript, CodeChickenLib,
ModularUI, Susy-Core, SussyPatches, ConfigAnytime, Supercritical, Gregicality
Multiblocks, Baubles and GTFO.
GroovyScript's original bundled Eclipse mapper/completion data classes are also
retained for linking the complete GT compatibility callback; no language server
is started. Every retained class and selected resource has artifact/hash provenance. These
dependencies are not bundled into the independently distributed engine. Existing
source-bounded owners still have explicit, recorded precedence.

The selected pack is Supersymmetry 0.1.16.15, commit
`3e83cd7bad57bd4c424de4e6cc707ab02fe32f54`, including Susy-Core 0.1.118 and
Supercritical 0.2.7. These are selected inputs, not a claim about the latest releases.
The selected Java 25 runtime remains a provisional Workbench choice, not proof
of the exact pack-installed JRE.

Supercritical's `SCElements` requires GT's `Element` to implement its native
`ElementExtension`. The original `MixinElement` supplies that interface, half-life
storage and accessors. The pack context selects this unchanged mixin and its
original refmap from the pinned artifact. It does not implement substitute fields
or catch and suppress the native cast failure.

Runtime assembly records the source configuration, selected class/refmap hashes
and excluded mixins. Bootstrap verifies the interface and observed merged mixin
on the actual native `Element` definition before candidate execution. The GT-only
context does not apply this transformation. Observing one required transformation
is not equivalence to the installed pack's complete mixin set.

## Ordinary authoring behavior

Native numeric boxing/unboxing, short coercion, comparisons, switch selection,
iteration and collection operations are admitted through exact policy entries.
The original JVM/Groovy operations still choose overloads and produce values or
exceptions. Native compiler-generated field access is allowed only for declared
source-owned data members. It does not open general reflective field access.

Complete-program differential tests retain unchanged `Battery`, `QuenchingFluid`,
`Carbons`, `GroovyUtils` and `Globals` source from the selected pack. They exercise
battery capacity, quenching-list registration, carbon traits/indexing, global
records/arrays, numeric loops and the native `event_manager` binding alias.
They do not claim that every method in those files has executed: for example,
battery item registration and GroovyUtils recipe removal remain separate work.

The same lane checks the native FluidBuilder temperature precondition with a valid
and invalid value. Axiom retains the original error, rather than adding a second
material-rule implementation. Run the lane with
`axiom_material_observation_conformance.py --authoring-only --pack-helper-authoring
--supersymmetry ...` and the explicit engine/runtime/native inputs.

The reference uses the original GroovyScript classloader and GT registration
section without the candidate gate or production observers. It shares native
API/content/platform dependencies with the installed operation: this is a bounded
behavioral comparison, not an independent whole-pack oracle.

## Incomplete context is not invalid developer source

The saved-workspace command now includes the complete selected config/ directory
as well as groovy/, retaining exact bytes and inventory identity through native
unpacking. Original configuration resources are preserved, not interpreted by a
replacement parser. Configuration is available inside the isolated worker before
bootstrap. Required-stack native configuration application is not fully qualified
and remains a context limitation; the bounded integration below does not close
that gap. Configuration capture is not proof that every captured mod initialized.

### Original conditional Susy-Core integration

The pack context requires saved `config/sussypatches.cfg`. It initializes the
original SussyPatches 1.11.6 `SusConfig`; the selected ConfigAnytime 3.0 registrar
loads that worker-local file through Cleanroom's original `Configuration` and
`ConfigManager.sync`. The worker verifies registration and the synchronized
`API.recipeInfo` field before invoking Susy-Core's original
`GrSModule.onCompatLoaded`. No host assignment substitutes for configuration.

That callback installs the original material expansions and FluidBuilder's
`basic()` only when `recipeInfo` is enabled. Descriptor-bounded admission allows
the original extension; native Groovy still dispatches it. When disabled, an
attempted `.basic()` call produces Groovy's native `MissingMethodException` and
saved-source location. Axiom does not manufacture the method or erase the
configuration condition. Other newly available extension methods are not
automatically admitted or qualified.

`execution.packConfiguration` records the effective setting, native property's
raw value and boolean-validity observation, input and worker-file hashes, and
the callback owner. A missing property uses the native default; a malformed
boolean also falls back according to Cleanroom's original parser. This is
observed native behavior, not Axiom declaring malformed configuration correct.
Normal native config saving can update the disposable worker copy. The saved
developer workspace and retained input bytes are never rewritten.

Run `tools/axiom_pack_configuration_conformance.py` with explicit `--java-home`,
`--engine-home`, `--runtime-home`, `--pack`, and a new `--report`; `--whole-pack`
also captures and verifies the unchanged selected checkout. It exercises both
settings, missing/default/malformed inputs, fresh-worker isolation, and native
source locations. It is a bounded regression lane sharing native dependencies,
not an independent whole-pack oracle.

GTCEu's original full `onCompatLoaded` callback now runs before Susy's callback.

until its addon prerequisites are composed; the GT-base content lane is retained.
Full container
discovery/blacklist handling, remaining configuration consumers and addon events

## Remaining composition and acceptance

Complete the original early transformation/class-definition transition, then
native selection/container/API/dependency/configuration state and late mixins,
then actual construction and Groovy bootstrap. The separate
[SERVER root check](native-root-class-space.md) supplies prerequisite evidence,
not a replacement for the current prepared-image material path. The temporary
host's dummy ownership/manual module state does not qualify real construction.

Compose MaterialEvent/PostMaterialEvent callbacks in native order, real registry
ownership, material expansions, custom/generated item/block coexistence and native
fluid completion for the supported stack and its actual dependencies. Keep
recipe-producing ore-prefix/handler work at its original later phase, not replayed
early just to finish a material observation. Recipe initialization then needs its
own original producers, registries and Groovy lifecycle before saved recipe
addition/change/removal can be accepted.

The bounded Susy-Core callback above is not proof of complete native callback
discovery, ordering, registry ownership or required-stack configuration equivalence.
An eventual scoped completed result requires evidence that no remaining gap affects
that scope; removing an incomplete guard alone is not an implementation.

Setup or observation failures outside the native log observer retain their original
throwable graph and an explicit host-context gap. Unobserved script indexes or
material state are not fabricated. A native error reached in incomplete context
must not be presented as proof that a developer's saved edit is invalid.

The acceptance target is an unchanged-checkout baseline for the declared
required-stack scope, representative saved material/item/fluid edits, native
failure and developer repair/rerun through the installed IDE workflow, followed
by native recipe registration/removal. Verify effective registry changes and
source-located logged/thrown errors. Axiom never repairs source itself. Bounded
helper tests do not satisfy that target. Recipe effects, generated fluid completion
and the full supported scope remain unqualified. Whole-pack/gameplay parity is
not an MVP gate. Minecraft is not launched.

Reproducible first-time preparation and exact intended installed-JVM qualification
are separate requirements. Existing cached inputs and saved-path setup do not
satisfy them. Measure performance only after the supported initialization scope
completes, then repeat installed CLI/IDE and frozen qualification against the final
identities. Earlier partial checks are useful evidence, not a completed-MVP timing.
