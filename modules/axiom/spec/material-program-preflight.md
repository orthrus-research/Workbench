# Native material-program preflight

Product direction: [native initialization-check MVP](initialization-mvp.md).
The developer edits; Axiom tests and reports. The required stack is GroovyScript,
CleanroomMC/Forge infrastructure (including MixinBooter and IVToolkit), GTCEu,
GCYM, Susy-Core, SussyPatches and Supercritical. Complete native execution of the
declared supported scope is the target, not initialization of every pack mod.
Automatic source repair is not part of this workflow.

Status: implementation in progress. The installed `material-program` operation
executes complete saved programs and returns native observations. It is not yet
qualified material validity. Saved-check CLI retention and the VS Code/IntelliJ
material-check interfaces are implemented. Native-backed editor/source tests pass
in the supported VS Code hosts and IntelliJ platform fixtures; full acceptance and
native program qualification remain pending.
Existing material-family conformance does not qualify this program path.

Native diagnostics are the default: no expectations file or material identity
selector is required. All saved source remains available and the selected lifecycle executes when admitted;
omitting selectors only omits selected-material observations and assertions.
A clean diagnostic run is not a qualified validity guarantee. The GT-base context
does not supply the complete addon material lifecycle. The separate
[pack context](pack-material-context.md) now supplies pinned addon classes and the
native Supercritical element transformation. Its original SERVER route follows
the profile's `initializationStage: recipes` selection. Original construction,
preInit, recipe events, init/postInit and load-complete run on the same native
state. Passive observations retain effective GT lookup storage, numeric crafting
registry order, stored ingredient/output/callback captures and furnace mappings.

The production scope is `original-preinit-through-available-recipe-registries`.
The evidence evaluator requires original lifecycle, configuration, server/biome
prerequisites, source coverage, diagnostic attribution and complete stored values.
A native pack error with an observed original artifact caller can coexist with
complete coverage, yielding outer `rejected` and `nativeOutcome: native-failed`.
It never becomes a clean pass or an assertion that saved source is invalid.
Supported saved-source failures retain `source-error` and their original locations.
A source failure during preInit can establish a failed initialization outcome
without claiming later recipe effects. Missing prerequisites, unexplained errors,
observer failures and incomplete stored values remain `incomplete`.

Installed Core acceptance covers the ordinary saved recipe baseline, native
runtime/compiler failures with exact historical source, and missing-JAR refusal.
Full recipe edit/IDE acceptance and final MVP qualification remain open. Core
retains complete recipe results, but the pretty-printed CLI response exceeds
Node's single-string capacity and cannot yet support the full recipe IDE route.
Installed assembly uses exact previously acquired inputs; fresh remote acquisition
of the expanded context remains unqualified after a pinned addon URL returned HTTP
403. The earlier installed startup/edit evidence retains its original scope.
Prepared pack runtimes require rebuilding; the bounded GT-base route is unchanged.

`execution.registrationEffects` and `execution.customMetaItems` retain one copy of
each observed collection. The nested native snapshot references these fields
through `snapshotEncoding.executionFields`, and its diagnostic lists reference
`/execution/diagnostics`. An optional `diagnosticEnvelopeCount` preserves additional
bootstrap failure rows separately from native and Groovy diagnostic channels.
`NativeStageSnapshots.expandExecution` restores the complete native state and exact
hexadecimal fingerprints for comparisons; the retained wire response is unchanged.
Generated catalogs join effect comparison when present. Missing or partial catalogs
remain not comparable and cannot be interpreted as deletions.

Optional `observeMaterials` and expectation-derived selectors now read the original
registry after the same complete preInit pass. Selected values reuse native material,
property and fluid-storage observers. Requested form facts come from the complete
generated collections and original eligibility, unifier and world-free ordinary-drop
getters. Generation, native selection and ordinary drop remain separate facts: an
existing vanilla iron block can be selected without a generated GT iron block.
Selectors do not select saved source or replay callbacks. The profile owns lifecycle selection; stored crafting callbacks remain deferred.

Explicit `observeMaterials` requests include all supported forms and the selected
material's membership in native prefix queues. Expectation-only requests retain the
forms, fluid state and prefix membership needed by those checks. Prefix queue scope
is explicitly limited to requested material identities; unrelated members are not
claimed absent. Selected collections share the execution envelope through the same
lossless snapshot references. MVP resource targets are temporarily suspended;
worker interruption or incomplete evidence still yields an incomplete result. Unknown vocabulary and
unavailable values remain unresolved, while known mismatches remain visible.

A saved-only GT configuration check demonstrates original configuration consumption:
changing `generateLowQualityGems` creates native chipped/flawed Diamond variants,
without changing Groovy source. Manual correction restores the original generated
collections. Passive observations also bind the selected original annotation config
classes to the Configuration objects synchronized during native construction and
to the saved config directory. They do not synchronize, load or save configuration.
This evidence does not prove applicability of every captured file or qualify later
recipe/configuration consumers.

The saved-content conformance lane also adds and modifies a material helper,
its dependent material, a fluid and a custom meta-item in the ordinary checkout.
Native effect comparison distinguishes new registry identities from changed
selected state, including the dependent material's derived color. Manual correction
restores the intended modified state; deleting the additions and their callers
restores the original baseline. Original item
and fluid property failures retain their exception causes and saved frames; a
missing helper retains the native compiler's import location. GT's logged legacy
component error remains visible even when native registration continues. These
observations do not waive completed-scope or installed-workflow qualification.

For explicit local pack runtime assembly, use the existing builder with
`--context supersymmetry:material-authoring-pack`, `--java-home`, `--engine-home`,
`--library-root`, `--server`, `--cleanroom`, `--foundation`, `--addon-inventory`,
`--pack`, `--program` and a new `--output`. These are original selected inputs;
prepared `--images`, `--api-program` and `--language-program` cannot be combined
with the pack route. The assembly archive verifies its baseline only and is not
packaged in the runtime. Core still captures fresh saved sources for each run.
The assembler shares Axiom's installed `native_assembly` compilation and staging steps. The
Axiom wheel carries the SERVER input-builder, annotation scanner and required host sources;
the step snapshots them and compiles through the caller's process service. It
preserves the selected classpath and original compiler failures. Installed Core
supervision reproduces the host classes and SERVER descriptor from those resources
with explicitly supplied, verified engine, platform and JVM inputs. This step
does not provision the engine or run initialization. Installed runtime assembly
uses those same steps and the original scanner through Core setup, as described below.
First-time engine provisioning remains open.

## Retained checks in the developer workflow

Install the optional `workbench-shell[material-checks]` dependency closure (or
install/enable `workbench-axiom` alongside Shell). Use the existing selected Work
Session, not a new studio or a captured game image. Save your IDE edits and run:

```sh
workbench context --state-root /private/developer-state select /checkout/pack \
  --pack-profile supersymmetry --platform-profile cleanroom \
  --variant cleanroom-provisional
workbench context --state-root /private/developer-state run SESSION -- checks materials contexts
workbench context --state-root /private/developer-state run SESSION -- checks materials setup \
  --context supersymmetry:material-authoring-gt-base \
  --engine-home /tools/axiom \
  --runtime-home /inputs/material-runtime
workbench context --state-root /private/developer-state run SESSION -- checks materials setup-status \
  --context supersymmetry:material-authoring-gt-base
workbench context --state-root /private/developer-state run SESSION -- checks materials run \
  --context supersymmetry:material-authoring-gt-base
workbench context --state-root /private/developer-state run SESSION -- checks materials show ATTEMPT
```

Replace `SESSION` and `ATTEMPT` with the exact returned identities. `run` captures
the current saved files and executes that new snapshot in one command. Every
invocation sees current saved additions (including untracked files), modifications
and deletions. Snapshots and request identities are retained internally; no archive
or fixture preparation is required. Unsaved editor buffers are not disk input.
The process exit code preserves the result: 0 for accepted scoped startup, 4 for
incomplete, and 1 for native source errors/expectation rejection or invocation
failure. Exact status and scope remain in the JSON; accepted startup is not
whole-pack validity.

For first-time raw input preparation, use the same selected Work Session:

```sh
workbench context --state-root /private/developer-state run SESSION -- checks materials setup \
  --prepare --context supersymmetry:material-authoring-gt-base
```

`setup --prepare` acquires the installed platform profile's exact original SERVER
artifacts through Core's shared verified artifact store. For
`supersymmetry:material-authoring-pack`, it also acquires the pack profile's complete
selected native recipe context, using original pack filenames and verified download
identities. The bounded GT-base context keeps its platform-only preparation.
The pack's `axiom-native-inputs.json` binds artifact sizes/SHA256, pinned descriptor
hashes and download metadata to the selected source revision and native context.
It preserves the declared
relative paths, including the Maven library layout, in private Core storage and
returns their location with state `inputs-prepared` and setup state `incomplete`.
The retained preparation binds the selected context, both profile owners and source
policy digests. Reruns verify and reuse those exact staged bytes; changed staged
files refuse reuse. Cancellation is checked before and after each artifact fetch
and copy and before publication; an in-flight fetch retains Core's existing I/O
timeout. A cancelled or failed attempt leaves setup incomplete, while verified
cache files can be reused on retry.

Without an engine input, preparation needs no JVM and does not create or replace a
runnable setup. `setup-status` stays `missing` until setup succeeds, or continues
reporting the previously saved setup. To assemble the required pack runtime:

```sh
workbench context --state-root /private/developer-state run SESSION -- checks materials setup \
  --prepare --context supersymmetry:material-authoring-pack \
  --engine-archive /downloads/workbench-axiom-engine-0.1.0.zip
```

Use the independent engine distribution from the matching release or candidate.
Core snapshots its exact ZIP through the existing artifact store, extracts it with
the shared Java archive service, and retains all distribution files and notices.
Axiom verifies the component/version, engine libraries and required notices;
context assembly also verifies the engine's selected source/platform bindings.
Verified retries reuse the retained engine; changed retained files refuse reuse.
Acquisition, extraction or compatibility failure preserves the previous setup.
An existing explicit `--engine-home /installed/axiom-engine` remains available in
place of `--engine-archive`. The Python integration wheel and independent engine
remain separate artifacts. Engine preparation does not require a build checkout.

Core reuses its selected Java; `--java /selected/jdk/bin/java` explicitly selects
the same profile-verified JVM when needed. Axiom verifies engine/source bindings,
JVM files and packaged resources, then compiles the original input builder,
scanner and host. The scanner reads the complete selected original JARs through
Cleanroom's ASMModParser without defining mod classes. The existing SERVER witness
builder and runtime staging preserve native artifacts, filenames and classpath order.
No source checkout, saved program, prepared native image or prior scanner inventory
is required for this installed assembly.

Core retains assembly inputs, process output and failures, and publishes the
runtime only after rechecking owner and artifact identities. Reruns verify and
reuse its runtime files without recompiling. Failed or cancelled assembly preserves
an earlier setup; runtime creation itself does not execute material initialization.
Successful assembly returns `configured-not-run`; normal saved checks then reuse it.
Omit `--runtime-home` and `--program-root` with `--prepare`. Routine `run` or
`prepare` commands use the saved engine/runtime selection without repeating those
paths or retaining the downloaded ZIP at its original location. Fresh Linux setup,
selected-JVM execution and both IDE startup error/correction workflows pass through
this managed selection. Recipe scope and final MVP qualification remain open.

Without `--prepare`, `setup` is an explicit one-time binding per selected workspace/context, retained
in private Core state. Engine and native runtime paths are still required. When
`--java` is omitted, setup reuses the Java selected by `workbench setup` from
Core's saved user setup record; it does not search `PATH` or infer a JVM from the
pack. An explicit `--java /tools/selected-jdk/bin/java` takes precedence. If Core
has no saved Java selection, configure it with `workbench setup` using a runtime
profile or supply `--java`. Either selection must pass the same exact profile JVM
byte checks. Temurin 25.0.4+7 Linux x86_64 is the deliberately selected Workbench
MVP runtime, with unchanged byte pins. This choice does not identify an upstream
pack-installed JRE. Installed/native startup-edit acceptance through fresh managed
setup passes for these exact bytes. Recipe and full MVP qualification remain open.
The `cleanroom-provisional`
platform variant and status remain unchanged.

Setup without `--prepare` verifies these inputs without executing Java or
downloading a replacement.
`setup-status` reports `missing`, `ready` or `stale`; ready means these bindings match, not that
the selected JVM or initialization scope is qualified. Each normal
`run`/`prepare` revalidates the setup and captures current saved input. Changed
inputs require explicit rebinding. Supplying all three engine/runtime/Java paths
remains an advanced per-invocation override and does not replace saved setup;
partial path overrides refuse. Both IDEs reuse prepared setup and offer explicit
reconfiguration and optional expectations without repeated path prompts.

The program directory defaults to the selected checkout root. Add
`--request checks/example-materials.json` only when saved observations/expectations
are wanted. Omission retains an empty request in private attempt storage, with no
invented source file or source mutation. An explicitly selected missing or invalid
file still refuses; it never silently falls back to diagnostics-only mode.
`--program-root authoring/example` explicitly selects a smaller program; selecting a
bounded program does not certify its enclosing pack. All files under the selected
`groovy/` and `config/` directories are captured; unsupported source/loaders and
configuration resources are not filtered out. Ignored files inside either
directory cause a completeness refusal. Files outside those directories are not
implicitly imported into the native program. A bounded program may omit config/;
absence never proves that an actual pack's required configuration is available.

The deterministic program identity binds both directories, including binary
configuration resources. Saved configuration additions, edits and deletions are
recaptured on each run and retained in paired inputs and file comparisons.
`sourceScope.configuration` records the configuration count/hash, references the
complete Core-retained program using
`inventoryReference={owner:core-retained-material-program,sourceProgramSha256:<digest>,filesPointer:/files}`,
and records the native application evidence separately. The pointer resolves
inside that retained program, not inside the native response. Capturing config
alone does not prove application. The original startup route requires complete
selected annotation bindings and saved directory identity; its evidence pointer
is `/execution/nativeInitialization/nativeConfiguration`. Other contexts retain
the configuration-application guard. Missing affecting bindings make startup
incomplete without discarding native messages or blaming the developer's edit. Config files ending
in `.groovy` are retained as configuration, not scheduled as source scripts.

Input limits are 4,096 files and 24 MiB total. Groovy retains its separate limit of
512 files, 8 MiB total and 1 MiB per file; configuration resources allow 4 MiB per
file. Exceeding a bound refuses intake rather than dropping content.

Native `sourceProgram` is an explicit `axiom.native-source-inventory-ack.v1`
acknowledgement containing exactly `schema`, `sha256`, integer `fileCount`,
`inventoryEncoding:sorted-path-recursively-key-sorted-json-utf8-v1`, and
`scope:all-submitted-groovy-and-config-files`. Native intake independently builds
the complete inventory from every original archive entry; it receives no expected
source digest to echo. Inventory paths sort by Unicode code point, including
supplementary characters, and recursively sorted JSON keys encode as UTF8.
Core retains full path/size/hash rows and exact source/archive bytes. The installed
CLI verifies the acknowledgement and both paired sides against complete captured
inventories; mismatches are incomplete invocation, never source invalidity.
An outcome carrying source/execution evidence must have an acknowledgement even
when its status is incomplete. Old inline-inventory receipts are not rewritten;
their unsupported custody schema refuses reopen explicitly.

The native intake preserves original `runConfig.json`, metadata such as
`groovy.iml`, and all source bytes. The profile admits the pack's ordered preInit
and postInit roots without rewriting their configuration. `sourceScope` reports
the selected loader, declared loaders and deferred source files. Cross-loader
imports can resolve natively; making a class available does not execute its
loader's script bodies. Structural admission currently inspects all Groovy files,
including deferred files: an unsupported feature may stop the run before native
compilation. Such an admission finding is not a native recipe-invalidity result.
The selected unchanged pack now reaches material producer execution, with native
context gaps retained; it is still not a native pass.

The selected profile admits the exact native `groovy.transform.TupleConstructor`
annotation without options, including an explicit import or alias. Groovy 4.0.30
performs the transform itself: Axiom does not generate substitute constructors,
remove annotations, or lower the saved source. Complete-program reference tests
exercise nested data classes, positional arguments, omitted trailing arguments,
field initializers, property assignment, and the native error for an unmatched
constructor. Groovy's generated nested-class dispatch bridges retain their bodies;
their native adapter calls pass through the existing operation checks. This does
not admit arbitrary annotations, compiler options, metaclass replacement,
or unrestricted inner-class fallback behavior.

The exact compiler-emitted `DefaultTypeTransformation.booleanUnbox(Object):boolean`
call is guarded by the existing cast policy before entering the original Groovy
helper. Native truth conversion, operand evaluation, short-circuiting and thrown
exceptions remain unchanged. The helper's possible `asBoolean` dispatch requires
an admitted receiver conversion; arbitrary receiver callbacks and direct access
to alternate compiler helpers remain refused. The helper is not an unrestricted
profile `compilerStaticCalls` entry.

The native `record` keyword is also admitted for the pack's `String`, `int`,
`boolean` and `double` component types. Groovy performs its own RecordType
transform and emits real JVM records on the selected Java 25 toolchain (class
version 69); Axiom does not select emulated records or change the compiler target.
Explicit RecordType/RecordOptions annotations and custom component transforms
remain outside this admission. Nested and top-level records retain native
positional/named construction, declared defaults, component access, value methods
and generated `getAt`/`size`/`toList`/`toMap` behavior. The JVM's original
ObjectMethods bootstrap is retained. The compiler's record metadata expression
and named-constructor selection remain native, not replacement implementations.

`execution.recordCompilations` retains class version, component descriptors and
original/guarded byte hashes. Reference comparisons require exact equality of the
original compiled record bytes before Axiom's dispatch checks. This is evidence
for these complete programs and inputs, not universal record equivalence.
Native failures preserve their original types/messages, including upstream
linkage errors. `execution.nativeSourceFrames` retains source-mapped generated
frames with unknown line numbers; only positive native lines become navigable
diagnostic locations. No generated frame is assigned a guessed source line.

Native keyword traits and `withTraits` composition of source-defined data classes
are admitted in this context. Groovy retains compilation, helper initialization,
ordered composition, field storage, delegated calls and method selection. Axiom
does not flatten a trait into its delegate or implement replacement precedence.
The bounded surface includes marker/inherited traits, String/int/boolean fields,
overlapping properties, `tap` edits, and native list `grep`, `size` and integer
index access. Explicit Trait annotations and default-method interfaces are not
implicitly admitted as keyword traits.

Groovy generates adapters and proxies through its own InnerLoader, outside the
normal source compilation hook. Axiom observes and checks that definition route;
generated identity includes the actual defining classloader, not just the class
name. `execution.traitCompilations` binds source traits/helpers to original and
guarded hashes; `execution.traitDefinitions` does the same for generated classes,
retaining ordered interfaces and a worker-local definition-scope ordinal. The
reference comparison requires identical source/helper and adapter bytes. For
reflection-emitted proxies it also compares a method-order-independent class hash:
only method declaration order is normalized for evidence, preserving all method
bodies and interface order. Normalized bytes are never executed.

Complete-program comparisons include the selected pack's unchanged
`globals/Sintering.groovy`, native property overlap/composition behavior, and
native material failure/correction through a trait. This does not establish
every Carbons/Petrochemistry/RubberChain method, arbitrary trait features,
machine/recipe validity, or whole-pack material-context closure.

This is a language capability within the bounded GT-base material context, not
qualification of the complete pack files which use it. Native RecipeMap
[metaclass extensions](native-recipe-map-extensions.md) now have a bounded
execution path, including original construction and direct-field semantics.
Actual addon/material producer composition and recipe-phase execution remain
separate unfinished requirements; structural admission alone is never validity.

In installed paired results, Core-owned `sourceComparison` lists saved files added,
removed and modified, independently of native observation comparison. It binds
both source digests and explicitly names `core-verified-saved-inputs` as owner.
The direct Java comparison instead returns `requires-retained-inventories`; its
descriptor is preserved as `nativeSourceComparison` when Core supplies the file
delta. Source deltas remain available when both inventories were acknowledged
even if native observations are not comparable. A removed recipe file is a source change, not proof that the
native recipe registry has been rebuilt or validated. Deferred loaders always
remain visible as incomplete workspace coverage in both IDE reports.

For deliberate two-step execution, use `prepare` with the same input options,
then `execute ATTEMPT --confirm REQUEST_ID`. IDE actions retain this internal
preparation/consent boundary to support exact cancellation and source custody.

Preparation retains exact bytes, modes and source observation, deterministic
program ZIP, original intent JSON, profile policies, installed engine identity
and selected toolchain inventory. It starts no JVM. Execution requires the exact
request ID, unchanged source/context and selected inputs. After execution begins,
developer edits are allowed: results remain bound to the saved candidate. Core
module enablement is checked against Core setup state, independently of the Work
Session storage location. The selected Workbench MVP JVM still requires
installed/native qualification; the runtime choice does not claim upstream
pack-installed JVM identity.

`run --baseline ATTEMPT` (or `prepare --baseline ATTEMPT`) retains a self-contained copy of that attempt's
complete program. Both programs run again in separate fresh native workers using
the **current** optional intent (or neither gets intent when it is omitted);
old native outcomes are not reused. The baseline
request identity remains provenance, not authority for its new execution.

`history` lists retained material attempts. `cancel ATTEMPT` signals Core's normal
bounded process path. A started attempt is never automatically rerun, and a start
marker without a result is not presented as proof of a live worker. Preparation
of a fresh attempt is explicit; no game-image recovery or launch is involved.

`show` verifies retained source/archive/intent/result custody without requiring
the old engine or native runtime to remain installed. It still needs the Axiom
Python package to interpret its retained contract. A changed current checkout is
presentation freshness, not grounds to reinterpret the historical native result.
Work Session owner references point to Axiom-owned request/result records.

The result's `state: completed` means invocation/result retention completed; it
does **not** mean valid material source. Read the unchanged `native.status`, native
lifecycle observations, expectations and qualification separately. Transport or
input-binding failures are `state: incomplete`, not source-invalid conclusions.
All current saved-check authority records explicitly deny qualified validity,
whole-pack parity, game launch and source mutation.

Each projected diagnostic has an exact pointer into the retained native response,
candidate/baseline identity and the original native location where available.
Verified editor coordinates are line-start points with exact SHA-256 and byte
offsets. Native columns remain separate; no expression span or column encoding
is guessed. Unknown paths and out-of-range lines remain unlocated.

Early Log4j events precede the source-aware Groovy observer. They retain the
original logger, severity, message and trace with unlocated source precision.
Saved checks project these events as Log4j findings; both IDE reports display
nonempty original traces with exact evidence pointers. A filename in trace text
does not establish a verified source location. Complete Axiom result retention
and history reopening have no MVP byte target, matching the native transport.

Native diagnostics retain `causality` (`axiom.native-diagnostic-causes.v1`): a
reported throwable root and an identity-preserving exception list with native
type, nullable message, ordered source frames, cause index and ordered suppressed
indices. Repeated frames and shared/cyclic exception identities are retained.
`observationLocations` separately identifies the logging/observation stack; it is
not an inferred exception origin. Compiler findings identify their owning native
exception and retain the compiler's location precision. Original traces remain
available, and messages/exception behavior are not rewritten.

The diagnostic's aggregate `locations` is a navigation index, not a cause chain.
Saved findings add `sourceRelationships` with exact exception/compiler/observation
pointers for each indexed location, including multiple relationships for a shared
frame. Both IDE reports label these native relationships and retain separate
baseline/candidate pointers; source identity, dirty-buffer and retained-source
rules still govern navigation. These relationships do not establish source blame,
material validity, or cause a diagnostic transcript to enter semantic comparison.
IDE finding details and source markers show the original wrapper message followed
by the types and messages of exceptions with native frames at that source. Logging
sites are not presented as exception origins, and the retained finding is unchanged.
`source ATTEMPT --diagnostic diagnostic-N` returns the exact retained file as a
read-only view even after the live file changes. Consumers must also verify the
individual location's bytes and reject dirty editor buffers before live navigation.
Both IDEs expose **Run Axiom material preflight** and **Reopen an Axiom material
check** inside the existing Saved Checks workflow. They select profile context,
complete program root, optional saved intent and explicit native inputs, then request exact
execution consent. A completed result can be selected as the source baseline for
a fresh developer-edit comparison. Readable reports keep native status, execution,
expectations and qualification separate. Candidate diagnostics decorate only
identical saved bytes; baseline diagnostics remain in the retained report. Changes
during a run or unsaved buffers suppress live annotations without retargeting or
cancelling the immutable check. Individual native findings can open retained
read-only source or the byte-verified working copy. These interfaces do not qualify
the native program or prove all IDE/native acceptance cases by their existence.
The VS Code host tests drive the shipped controller with scripted dialog answers

## Available invocation

The Java distribution exposes `material-program --runtime-home DIRECTORY
--program SOURCES.zip`. The Workbench module exposes the same operation through
the existing Core process port, without needing a JSON request for diagnostics:

```sh
workbench axiom material-program \
  --engine-home /tools/axiom --java /tools/selected-jdk/bin/java \
  --runtime-home /inputs/material-runtime --program /inputs/material-program.zip \
  --profile supersymmetry --context supersymmetry:material-authoring-gt-base
```

Optionally add `--request /inputs/observe.json` for observations, developer
expectations, or both (`{}` explicitly selects neither):

```json
{"observeMaterials": ["supersymmetry:example_material"]}
```

An expectation selects a native fact, not a recipe/material rule to simulate:

```json
{
  "expectations": [
    {"id":"dust-property", "material":"supersymmetry:example_material",
     "kind":"property", "key":"dust", "equals":true},
    {"id":"required-plate", "material":"supersymmetry:example_material",
     "kind":"form", "family":"gt-prefix-items", "prefix":"plate",
     "fact":"generated", "equals":true}
  ]
}
```

Every expectation has a unique `id`, exact `material` identity, `kind` and `equals`.
Referenced materials are automatically included in the observation selection.

| Kind | Additional selector | Native observation |
| --- | --- | --- |
| `registration` | None; boolean expected | Exact resource identity and actual storage-registry membership |
| `value` | `key`: `id`, `color`, `formula`, `storageRegistry` | Integer or string returned by the original material/registry; formula may explicitly be null |
| `property` | `key`: native property name; boolean expected | Membership among the selected GT property declarations |
| `property-value` | `key`: property, `field`: selected getter field | Actual native scalar property value; supported tool fields are listed below |
| `flag` | `key`: native flag name; boolean expected | Original `hasFlag` result for the selected GT declaration |
| `form` | `family`, `prefix`, `fact`; boolean expected | `generated` variant, `selected` unifier stack, prefix `eligible`, or ore `ordinaryDrop` |
| `fluid` | `storageKey`, `fact`: `queued` or `stored`; boolean expected | Actual pending builder or stored fluid membership for a native storage key |
| `processing` | `prefix`, `fact`: `queued`; boolean expected | Actual material membership in a native prefix's pending processing set; not handler execution |

Form families are `gt-prefix-items`, `gt-material-blocks` and `gt-ore-blocks`.
Ore assertions additionally require the exact `stone` name. Eligibility is
observed only for prefix items; ordinary drops only for generated ore variants.
Names are native vocabulary identifiers, not case-folded aliases. Unknown property,
flag, family, prefix or stone vocabulary is unsupported, not an observed absence.
Property/flag lists are readonly native-declaration membership observations.
Scalar observation currently covers the ten ToolProperty getters below, not
arbitrary addon properties, enchantment maps or every property's scalar fields.

Tool scalar selectors use `key: "tool"`. Float fields are `toolSpeed`,
`toolAttackDamage` and `toolAttackSpeed`. Integer fields are `toolDurability`,
`toolHarvestLevel`, `toolEnchantability` and `durabilityMultiplier`. Boolean
fields are `shouldIgnoreCraftingTools`, `unbreakable` and `magnetic`.

For example, `{"id":"tool-speed", "material":"supersymmetry:example_material",
"kind":"property-value", "key":"tool", "field":"toolSpeed", "equals":4.0}`
compares developer intent with the original native getter. These checks run in
the existing saved-program workflow, including fresh baseline/candidate pairs.

`execution.materials[].propertyValues.tool` retains typed scalar records such as
`{"type":"float32", "value":4.0, "rawBits":"40800000"}`. Finite floats use
JSON numbers plus their exact eight-digit raw IEEE-754 bits; non-finite floats
use explicit `"NaN"`, `"Infinity"` or `"-Infinity"` strings plus raw bits, never
invalid JSON numeric tokens. Intent can use those three strings. Numeric intent
equality treats positive and negative zero as equal, while raw bits remain

## Contract

The operation evaluates a complete, explicitly declared source program in a
profile-owned native context. It must use the selected JVM, the qualified native
GroovyScript compiler/dispatch/transformations, and one original-name material
class space through registration and generated content. It is not the existing
recipe AST interpreter and does not translate source into a new material DSL.

The initial context selection is
`supersymmetry:material-authoring-gt-base`, owned by the installed Supersymmetry
profile. It composes the complete qualified GT material catalog with the supplied
program's listeners. Its registry owner is `gregtech`; resource namespace and
script owner are separate native facts. No `supersymmetry` material registry is
invented to make those names agree. Susy-Core and the pack's full listener
composition are excluded, not treated as having run successfully.

`tools/axiom_material_pack_boundary.py` verifies this limit against the complete
pinned `RegisterMetaItems.groovy` and `OreMaterials.groovy`, each added unchanged
to the declared authoring program. Their missing globals, GT item support, and
Susy dependencies produce source-located native compiler findings and incomplete
coverage. Native continuation can still register the base program's materials
and generate their forms; that success cannot qualify the additional whole file.
The witness binds every saved byte and its selected Git identity. It is not a
whole-pack invocation or permission to strip unsupported declarations.

The source input is an immutable saved candidate, including its complete declared
program and run configuration. Existing source-target/overlay custody should be
reused for pack-backed candidates; standalone programs need equally explicit
file membership and exact-base identity. A request selects an installed context,
not a host classpath, native implementation, process entry point or safety policy.
The compiler owns source loading/order, including native preprocessor decisions;
sorting a fingerprint inventory must not reorder execution.

The context's `pending-native-groovy-execution` state prevents treating selection
metadata or available execution as qualified support. A future accepted invocation must additionally
bind qualified engine/program images, compiler libraries, transformations,
configuration and the selected JVM. Each invocation gets a fresh isolated worker.

## Result meaning

`result.initialization` (`axiom.scoped-initialization.v1`) summarizes the declared
loader scope, execution checkpoint, coverage, native-error observation and
blocking evidence pointers. `completed`, `native-failed` and `incomplete` are
different outcomes; the current unqualified contexts remain **incomplete** even
when their bounded native checkpoint returns. An observed native exception can
coexist with an incomplete context and is not automatically developer blame.
Original bootstrap causes remain visible even if transformer observation fails.

`execution.registrationEffects` is passive current-state evidence. Material
identities and selected native properties have complete digest inventories without
MVP byte or entry-count targets. Complete selected-pack membership still requires
native measurement. Fluids use actual
Forge registry membership, not queued builders. Custom-item effects reference
native owner/meta definitions and their selected values; a definition is not
proof of owner Forge registration. Paired `effectComparison` reports native
identity additions, removals and modifications, including same-count edits.
Different checkpoints or incomplete inventories are not comparable. Recipe
effects remain unchecked. This does not establish complete material/item/fluid
effect coverage or explain source causation.

Both individual worker output and the final inline pair retain complete serialized
UTF8 evidence, including installed custody and saved-file delta projection. MVP
output budgets are temporarily suspended. Native observation or process failures
still remain explicit; no partial inventory is promoted to completion.

Keep execution completion, coverage, native outcomes, developer expectations and
source freshness separate. A native error logged without a throw is still an
observed semantic error. Native registration can return an object while refusing
registry membership. An absent item form is not necessarily an invalid material.
An unqualified dependency or host termination is not automatically a source error.

Generated-form observations distinguish three native facts: the prefix's
generation condition, the family's actual registered variant, and the stack
selected by ore unification. These are not interchangeable. An ignored GT prefix
can select an existing vanilla item without generating a GT variant; a missing
plate can be the correct result for a material without its generation flag.
Keep item registry identity, metadata, material identity and ore membership with
the observed stack. Prefix-item registration does not run recipe handlers or
establish block/ore, custom-item or machine-behavior coverage.

The composed block family retains native material-ID grouping and metadata slots,
BlockStates, property serialization and ItemBlock binding. Ore forms additionally
retain the host stone identity. A generated ore variant, an item selected by the
unifier, and an ordinary dropped item can differ; report them separately. This
does not establish world generation or harvesting-event behavior.

Only a completed program/checkpoint with sufficient qualified coverage, no
disqualifying native errors, and satisfied explicit expectations can pass.
Catching an unqualified-operation failure in source cannot restore coverage.
Skipped source and successful excerpts cannot confer whole-file or pack validity.

Diagnostics retain original paths and candidate digests, native causes, and the
location precision actually available. Deferred listener errors retain their
source origin. Instrumentation must not change expression count, native dispatch,
ordering or outcomes. New or unsaved editor content must not receive decorations
from an older candidate, although retained evidence remains inspectable.

GroovyScript's own error collection/log and GT's Log4j messages are distinct
channels. A component error can be logged while generation continues; a setter
exception can leave registered materials and earlier edits intact while stopping
before generation. A refused late registration can return a constructed material
without adding it to the registry. Preserve these outcomes rather than rolling
back state or treating completion as acceptance.

Isolation precedes compilation, class initialization and AST transformation.
Use the existing Linux process supervisor and Core custody/cancellation/cleanup
services, with compile-time and runtime containment requalified. Candidate output
must not become trusted response framing; shadowing trusted packages or forging

writes are admitted, and there is no unrestricted fallback.

installed Axiom module, with explicit profile context selection and no Minecraft,
